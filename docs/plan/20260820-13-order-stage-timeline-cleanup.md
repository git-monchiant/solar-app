# ขั้น Order: ยุบแถวชำระเงินที่ซ้ำ และแก้ยอดงวดที่ยังไม่ชำระ

วันที่: 2026-08-20
สถานะ: done

## 1. แถว "ยืนยันการชำระเงิน งวดที่ N" ซ้ำกับแถวแผนชำระ

แถวแผนชำระของแต่ละงวดจบบรรทัดด้วย "ยืนยันรับเงินโดย &lt;ชื่อ&gt; &lt;วันเวลา&gt;"
อยู่แล้ว ส่วน activity `payment_confirmed` ของงวดเดียวกันพูดซ้ำอีกแถว
ขั้น Order ของ Lead 691 จึงมี 5 แถวเพื่อเล่าเรื่องที่ใช้ 3 แถวก็พอ

ตอนนี้ตัดแถว `payment_confirmed` ออกเมื่อแถวแผนของงวดนั้น **รายงานการยืนยัน
จริง ๆ** เท่านั้น งวดที่ยังรอบัญชียืนยัน หรือการชำระที่ไม่อยู่ในแผน
ยังมีแถวของตัวเองเหมือนเดิม

## 2. ยอดงวดที่ยังไม่ชำระคำนวณจากฐานผิด

ยอดในแถวแผนใช้ลำดับ: ยอดที่ชำระจริง → คำนวณจาก % → ไม่แสดง
ขาที่สองเดิมคูณ `order_total` ดิบ ๆ ซึ่งเป็นราคาก่อนส่วนลดและยังไม่หักค่าจอง
งวดที่ยังไม่ชำระจึงแสดงยอดสูงเกินจริง

ฐานที่ถูกต้องคือสูตรเดียวกับ `OrderStep`:

```
netTotal = (order_total | quotation_amount) − ส่วนลด − ค่าจองที่ชำระแล้ว
```

ตรวจกับ Lead 691: 225,000 − 6,750 (3%) − 1,000 = 217,250 → งวด 20% = 43,450
และ 80% = 173,800 ตรงกับยอดที่เก็บจริงทุกบาท ยืนยันว่าข้อมูลไม่ได้ผิด
ผิดเฉพาะขาคำนวณสำรองใน Timeline

กระทบ 13 ใบที่มีส่วนลด และทุกใบที่มีค่าจอง

## 3. บันทึกผลตรวจ SLA ของขั้น Order (ยังไม่แก้)

| Policy | สถานะ |
| --- | --- |
| `DEPOSIT_CLOSE` | ทำงานปกติ |
| `LOAN_PREAPPROVAL` | ปกติ — `OrderStep` มีปุ่มบันทึก `loan_documents_complete` / `loan_preapproved` ที่ตรงกับ anchor แล้ว ยังไม่มีใบไหนเลือกจ่ายด้วยสินเชื่อจึงยังไม่มี instance |
| `PAYMENT_INSTALLMENT_1` | **ไม่เคยสร้าง instance เลยทั้งฐานข้อมูล** |

`PAYMENT_INSTALLMENT_1` ผูก anchor กับ activity ชื่อ "ส่งใบเสนอราคาให้ลูกค้า"
ซึ่งมีอยู่ 0 รายการ — ระบบใบเสนอราคาปัจจุบันเขียน title อื่น และคอลัมน์
`quotation_sent_date` ที่จะใช้แทนก็มีข้อมูลแค่ 5 ใบจาก 458 (Lead 691 เอง
ก็ไม่มี ทั้งที่ติดตั้งจบแล้ว) อีกทั้งวัดเรื่องเดียวกับ `DEPOSIT_CLOSE`
คือจบเมื่อยืนยันเงินงวดแรก ต่างแค่จุดเริ่มและกำหนด

ผู้ใช้เลือก **ปล่อยไว้ก่อน** — ไม่ยกเลิกและไม่เปลี่ยน anchor
บันทึกไว้ที่นี่เพื่อไม่ให้เข้าใจผิดว่าเป็นกติกาที่ทำงานอยู่
