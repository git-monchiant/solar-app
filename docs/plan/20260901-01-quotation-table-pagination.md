# ตารางรายการใบเสนอราคาล้นหน้า → ขึ้นตารางหน้าใหม่ (+ เปลี่ยนกระดาษเป็น A4)

สถานะ: done · 1 กันยายน 2569

## ปัญหาเดิม

ใบเสนอราคาถูกออกแบบเป็น **2 หน้าตายตัว** และ `.page` ตั้ง `overflow:hidden` ไว้
ถ้ารายการยาวเกินหนึ่งหน้า ตารางจะดันบล็อกยอดเงินตกขอบแล้ว "ถูกตัดทิ้งเงียบ ๆ"
(ยอดรวมและตัวหนังสือจำนวนเงินหายจากเอกสารสัญญาโดยไม่มี error) ระบบจึงแก้ด้วยการ
**ห้ามไม่ให้ส่งอนุมัติ** เมื่อรายการเกินความจุ — ผู้ใช้ต้องไปย่อชื่อรายการเอง

จุดที่ล็อกจำนวนหน้าไว้:

| ไฟล์ | สิ่งที่ล็อก |
|---|---|
| `quotation-pdf/[id]/route.ts` | `getPageCount() !== 2`, `pageCount !== 17`, footer `หน้า 16 / 17`, header `X-Quotation-Document-Pages: "17"` |
| `quotation-page-fit.ts` | ความจุ = `26 − จำนวนงวดชำระ` บรรทัด |
| `quotation-document.ts` | `validateQuotationDocument()` ขึ้น error เมื่อเกินความจุ |
| `QuotationBuilder.tsx` | badge แดง `used / capacity บรรทัด` |
| `quotation-approvals/page.tsx` | ข้อความ "เอกสารทั้ง 17 หน้า" และ badge `17 หน้า` |

## แนวทางที่เลือก

**วัดจริงด้วยเบราว์เซอร์ แล้วหั่นหน้าเองในโค้ด** (ไม่ปล่อยให้ Chrome แบ่งหน้าเอง
เพราะ watermark / เลขหน้า / หัวเอกสาร เป็น absolute จะคุมไม่ได้)

1. เรนเดอร์ "เอกสารสำหรับวัด" (`.page.probe` = `height:auto;overflow:visible`) หนึ่งรอบ
   อ่านความสูงจริงของหัวเอกสารเต็ม หัวย่อ หัวตาราง **แต่ละแถว** บล็อกท้าย และแต่ละ
   หัวข้อเงื่อนไข
2. ส่งตัวเลขเข้า `paginateQuotationRows()` (ตรรกะบริสุทธิ์ อยู่ใน `quotation-page-fit.ts`
   เทสต์ได้) เพื่อหั่นแถวเป็นหน้า ๆ
3. ประกอบ `<section class="page">` ตามผลที่ได้ แล้วค่อยพิมพ์

ทั้ง PDF และตัวอย่าง HTML เดินผ่านทางเดียวกัน จึงแบ่งหน้าเหมือนกันเป๊ะ

## กติกาความสวยงามที่บังคับไว้

1. หัวตาราง (ลำดับ / รายการ / จำนวนเงิน) ซ้ำทุกหน้า
2. หน้าต่อใช้หัวเอกสารย่อ — โลโก้ + `ใบเสนอราคา (ต่อ)` + เลขที่ใบ + ลูกค้า/โครงการ
   (เอกสารที่หลุดจากชุดยังบอกได้ว่าเป็นใบไหนของใคร และเหลือที่ให้ตารางมากกว่าหน้าแรก)
3. **ไม่ใส่แถวยอดยกไป/ยอดยกมา** — เคยทำไว้ตามมาตรฐานเอกสารการเงิน แต่ถอดออกตาม
   ที่ผู้ใช้ขอ เพราะกลัวลูกค้าเห็นตัวเลขกลางคันแล้วสับสนกับยอดสุทธิ ความต่อเนื่อง
   สื่อด้วยหัวย่อ "ใบเสนอราคา (ต่อ)" + เลขหน้า `ใบเสนอราคา i / m` แทน
   ถ้าอยากได้กลับมา ใส่แถวท้าย/หัวตารางเพิ่มแล้วบวกความสูงแถวนั้นกลับเข้า
   `paginateQuotationRows()` (หน้าต่อ 1 แถว + หน้าที่ยังไม่จบอีก 1 แถว)
4. แถวหัวข้อห้ามค้างท้ายหน้าโดยรายละเอียดไปขึ้นหน้าใหม่ และรายละเอียดบรรทัดสุดท้าย
   ของกลุ่มห้ามไปยืนเดี่ยวบนหน้าใหม่ (`avoidOrphanRows`)
5. บล็อกท้าย (งวดชำระ + ธนาคาร/QR + สรุปยอด + ตัวหนังสือจำนวนเงิน) อยู่หน้าเดียวกับ
   แถวสุดท้ายเสมอ ถ้าไม่พอที่จะได้หน้าของตัวเอง
6. หน้าที่ยังไม่จบตาราง **เผื่อแถวว่างไว้ 2 แถวแล้วปล่อยขาว** (`TRAILING_BLANK_ROWS`)
   — ลองมาแล้วทั้งสองสุดขั้ว: ลากกรอบจนสุดหน้าได้แถวว่างสิบกว่าแถว อ่านแล้วเหมือน
   ฟอร์มยังกรอกไม่เสร็จ · จบห้วนตรงรายการสุดท้ายก็เหมือนตารางถูกตัด · 2 แถวกำลังดี
   จำนวนถูกตัดด้วยที่ว่างจริงที่เหลือ (`min(2, slack / ความสูงแถวว่าง)`) หน้ากลาง ๆ
   ของใบยาวที่เต็มอยู่แล้วจึงได้ 0–1 แถวโดยไม่ล้น
   หน้าที่จบตาราง **ไม่เผื่อ** เพราะบล็อกยอดเงินต่อทันที ถ้าเผื่อจะกลายเป็นช่องว่างคั่น
   และยังเติมถึง 9 แถวเท่าเดิม — คงหน้าตาใบสั้น ๆ ซึ่งเป็นใบส่วนใหญ่ไว้ไม่ให้เปลี่ยน
7. เลขหน้าไดนามิก `หน้า X / N · ใบเสนอราคา i / m`
8. เงื่อนไข/ข้อกำหนด **ไหลทีละบรรทัด** ตามที่วัดได้จริง (เดิมเดาจากจำนวนแถว
   `itemRows.length > 9 / > 14` แล้วเปลี่ยนเป็นยกทีละหัวข้อ — พอหัวข้อถัดไปไม่พอที่
   ก็ทิ้งช่องว่างค้างไว้ครึ่งหน้า) หัวข้อห้ามค้างท้ายหน้าโดยไม่มีข้อไหนตามมา
   ที่เหลือไหลไปหน้าท้ายเล่มพร้อมลายเซ็น

## เปลี่ยนกระดาษใบเสนอราคาจาก Letter เป็น A4

เดิมเล่มเดียวมีกระดาษ **2 ขนาดปนกัน** — รายงานสำรวจ 15 หน้าแรกเป็น A4 (210×297mm)
แต่ใบเสนอราคาเป็น **US Letter** (215.9×279.4mm) จาก `@page{size:Letter}` +
`preferCSSPageSize:true` เวลาพิมพ์ A4 ทั้งเล่มหน้าใบเสนอราคาจึงโดนย่อ ~97%
หรือโดนตัดขอบข้างละ ~3mm

- ใบเสนอราคา: `@page{size:Letter}` → `size:210mm 297mm` · `.page` → `210mm × 297mm`
- รายงานสำรวจ: เพิ่ม `@page{size:210mm 297mm;margin:0}` และเปลี่ยน `format:"A4"`
  → `preferCSSPageSize:true` (ของ Chrome คือ 8.27×11.69in = 210.2×296.9mm
  ไม่เท่ากับ `.page` ที่เขียนไว้ 210×297mm เป๊ะ)
- route `survey-report/[id]` ที่ออกรายงานเดี่ยวยังใช้ `format:"A4"` เหมือนเดิม
  (`preferCSSPageSize` เป็น false อยู่แล้ว `@page` ที่เพิ่มจึงไม่มีผลกับ route นั้น)

ผล: **ทุกหน้าในชุดเป็น 209.89 × 297.01mm เท่ากันหมด**

หน้าสูงขึ้น 17.6mm แต่แคบลง 5.9mm → ความจุต่อหน้าเพิ่มขึ้น วัดจริงด้วย headless
Chrome ได้ **27 − จำนวนงวด** แถวต่อหน้าที่จบในหน้าเดียว (เดิม Letter คือ 26 − n)
ค่าประมาณใน `quotation-page-fit.ts` คาลิเบรตใหม่จากค่าที่วัดได้จริง (หน่วย "บรรทัด" 5mm):
`usable 55.0` · `firstHeader 11.2` · `contHeader 4.33` · `thead 1.12` ·
`row 1.05` (แถวจริงสูง 5.25mm ไม่ใช่ 5mm — 25 แถวคลาดกันเกิน 1 บรรทัดถ้าปัดทิ้ง) ·
`tail 14.56 + 0.92n`

## บีบพอดีหน้าเมื่อ "ขาดอีกนิดเดียว" (compact-fit)

วัดใบ SSR-QT-26-0038 (25 รายการ) พบว่าเสียไปทั้งหน้าเพราะเรื่องเล็กมาก:

| | mm |
|---|---|
| พื้นที่ตารางบนหน้า 1 | 215.4 |
| 25 รายการกิน | 135.4 |
| ที่ว่างเหลือ | 80.0 |
| บล็อกยอดเงิน (ไม่นับช่องว่างคั่น) | 79.1 |
| บล็อกยอดเงิน + **ช่องว่างคั่น 8mm** | 87.1 → ไม่พอ |

เหลือ 80 ต้องใช้ 79.1 — แค่ "แถวช่องว่างคั่น 8mm" ทำให้ทั้งบล็อกเด้งไปหน้าใหม่
แล้วที่ว่าง 80mm นั้นกลายเป็นแถวว่าง 15 แถวบนหน้า 1

แก้ด้วยคลาส `.compact-fit` ที่บีบ 3 จุด รวมได้คืนราว 14mm:

| บีบตรงไหน | ได้คืน |
|---|---|
| ช่องว่างคั่น 8mm → 3mm | 5.0mm |
| แถวตาราง 5.25mm → 5mm (ค่าตั้งต้นเดิมของ `.quote-table`) | 0.25mm × จำนวนแถว |
| กล่องธนาคาร/QR min-height 25mm → 22mm, padding 3mm → 2mm | 3.0mm |

รอบวัดเดิมวัด **ทั้งสองแบบในเอกสารเดียว** (ชุดปกติ + ชุดใต้ `.compact-fit`) ไม่ได้
เพิ่มรอบเรนเดอร์ แล้วแบ่งหน้าทั้งสองแบบเปรียบเทียบกัน — **ใช้แบบบีบเฉพาะเมื่อลด
จำนวนหน้าได้จริง** ใบที่จบในหน้าเดียวอยู่แล้วจึงไม่มีทางเข้าเงื่อนไข หน้าตาไม่เปลี่ยน

ผล: ใบ 25 รายการกลับมาจบใน **หน้าเดียว** (ชุดเต็ม 17 หน้า) · เพดานใบหน้าเดียวขยับ
จาก 25 เป็น ~26 รายการ

ใบที่รายการมากกว่านั้นยังได้หน้าที่แบกเฉพาะบล็อกยอดเงิน — ช่องว่างบนหน้านั้นแก้ต่อ
ในหัวข้อถัดไป

## กำจัดช่องว่างบนหน้ายอดเงินและหน้าลายเซ็น

วัดใบ 28 รายการ (ชุดเงื่อนไขมาตรฐาน) ตอนยังยกเงื่อนไขทีละหัวข้อ:
หน้ายอดเงินจบที่ข้อ 2.4 แล้ว **ว่าง 124.6mm** เพราะหัวข้อ 3 ทั้งก้อนไม่พอที่
ส่วนหน้าท้ายมีเงื่อนไข 62.8 + ลายเซ็น 78 = ว่างอีก 75.8mm — ช่องว่างสองก้อนบนสองหน้า

แก้สองชั้น:

**1. เงื่อนไขไหลทีละบรรทัด** — แบไต๋ทั้งชุดเป็นรายการบล็อก (หัวข้อ 1 บล็อก · แต่ละข้อ
1 บล็อก) วัดต้นทุนสะสมของทุกบล็อก แล้วตัดตรงที่พอดี พร้อมกันหัวข้อกำพร้าท้ายหน้า
→ ช่องว่างหน้ายอดเงินลดจาก 124.6 เหลือ 69.4mm (เงื่อนไขลงครบทั้ง 4 หัวข้อ)

`page2LeadingParagraphs` (ข้อที่ชุดมาตรฐานตั้งใจให้คร่อมสองหน้า) ถูกรวมมาเป็นกองเดียว
จึงต้องจับกลับไปต่อท้ายหัวข้อของตัวเองด้วยเลขข้อ (`"2.5)"` → หัวข้อ `"2."`) ก่อนแบไต๋
ไม่งั้นลำดับการอ่านจะสลับเมื่อมีหลายหัวข้อคร่อม และมีตัวรับเศษที่จับคู่ไม่ได้กันข้อความหาย

**2. ยุบลายเซ็นขึ้นมาต่อท้าย** — เมื่อเงื่อนไขลงหน้ายอดเงินได้หมด หน้าท้ายจะเหลือแต่
ลายเซ็นลอยบนกระดาษเปล่าทั้งแผ่น วัด `signaturesCost` (ต่อท้ายเงื่อนไขจริง) ทั้งแบบปกติ
และแบบบีบ `.tight-signatures` (ระยะบน 13→7mm · ระหว่างแถว 9→5mm · ความสูงขั้นต่ำ
ของช่อง 28→26mm ซึ่งยังกว้างกว่าเนื้อหาจริงราว 23.5mm) ได้คืนราว 14mm แล้วยุบเมื่อ
ที่ว่างพอ — เคส 28 รายการขาดแบบปกติอยู่ 0.6mm แต่แบบบีบลงพอดี

ผล: **28 และ 34 รายการ จาก 3 หน้าเหลือ 2 หน้า** · 45 รายการยังเป็น 3 หน้าแต่หน้ากลาง
แน่นแล้ว (เหลือเฉพาะลายเซ็นที่ 64mm ยังไม่พอลง) · ใบชุดเงื่อนไขสั้น 5 รายการ → **1 หน้า**

ใบปกติไม่กระทบ — id 88 หน้า 1 เหลือที่แค่ 8.5mm อยู่แล้ว จึงแทบไม่มีอะไรถูกดึงขึ้นมา
(ขยับขึ้นได้ 1 บรรทัด) และจำนวนหน้าเท่าเดิมทุกใบจริง
