# Timeline: milestone ก่อน แถว SLA ปิดท้ายขั้น

วันที่: 2026-08-20
สถานะ: cancelled

> ทำครบทุกขั้นแล้ว แต่พอไล่ดูของจริงทีละขั้น (Survey → Quotation → Install)
> ปรากฏว่าการเรียงตามเวลาจริงอ่านถูกต้องกว่าทุกครั้ง เพราะนาฬิกา SLA
> เปิดก่อนงานที่มันวัดเสมอ กติกานี้จึงถูกถอดออกทั้งหมด และโค้ดที่เกี่ยวข้อง
> (`SLA_AFTER_MILESTONE_SECTIONS`, `slaLast`) ถูกลบทิ้ง
>
> เอกสารนี้เก็บไว้เป็นบันทึกว่าเคยลองอะไรและทำไมถึงไม่เอา
> ข้อยกเว้นของขั้น Quotation ที่ไม่พับการเปลี่ยนสถานะ ถูกแทนที่ด้วยแผน 12
> ที่เลิกพับทุกขั้นแล้ว

## ปัญหา

ทุกขั้นเรียงทุกแถวตามเวลาล้วน แต่แถว SLA ถูกเรียงด้วย `started_at` คือเวลาที่
นาฬิกาเริ่มเดิน ไม่ใช่เวลาที่งานเสร็จ แถว SLA จึงไปนั่งกลางเหตุการณ์ที่ตัวเอง
กำลังตัดสินอยู่

ตัวอย่างขั้น Survey: "ยืนยันนัดสำรวจ 22 มิ.ย." → "เข้าตรวจสำรวจหน้างาน (SLA
เริ่ม 22 มิ.ย. เสร็จ 26 มิ.ย.)" → "เข้าสำรวจหน้างานจริง 26 มิ.ย."
อ่านแล้วเรื่องกระโดด: นัด → คำตัดสิน → ผลจริง

## กติกาใหม่

ในแต่ละขั้น milestone เล่าเรื่องก่อนตามลำดับเวลา แล้วปิดท้ายด้วยแถว SLA
ของขั้นนั้น — รูปแบบเดียวกับที่ Pre-Survey เป็นอยู่ คือเปิดด้วย
"ลงทะเบียน Lead" แล้วตามด้วยแถว SLA ทั้งชุด

ใช้กับ Order, Install, Warranty / After Sales และ Grid-Tie
(ขั้น Grid-Tie ยังไม่มี SLA จึงยังไม่เห็นผล แต่ใส่ไว้ให้พร้อม)

Pre-Survey, Survey และ Quotation ยังเรียงตามเวลาล้วน เพราะทั้งสามขั้น
นาฬิกาเริ่มเดินก่อนงานที่มันวัด — ลงทะเบียน Lead, วันนัดที่ยืนยันแล้ว และ
วันที่สำรวจเสร็จ ตามลำดับ เวลาจริงจึงเรียงถูกอยู่แล้ว:

- **Pre-Survey** ที่นั่นแถว SLA **คือ** เนื้อเรื่อง (6 แถว SLA ต่อ milestone
  1 แถว) ถ้าเลื่อน SLA ไปท้ายก็เท่ากับย้ายทั้งขั้นลงไปกองล่าง
- **Survey** ได้ลำดับ ยืนยันนัด → เข้าตรวจสำรวจหน้างาน (SLA) → สำรวจเสร็จ
  และเข้าสู่ขั้นใบเสนอราคา
- **Quotation** ได้ลำดับ จัดส่ง Proposal (SLA) → ลูกค้ายืนยัน

ภายในกลุ่ม SLA ยังเรียงตาม `started_at` เหมือนเดิม ขั้นที่มี SLA หลายตัว
อย่าง Order (มัดจำ, งวดที่ 1, สินเชื่อ) จึงยังเรียงตามลำดับที่นาฬิกาเริ่มเดิน

## ข้อยกเว้น: ขั้น Quotation ไม่พับการเปลี่ยนสถานะ

ขั้น Quotation ไม่มี milestone เป็นของตัวเองเลย มีแต่แถว SLA "จัดส่ง Proposal"
ส่วนหลักฐานว่าลูกค้าตอบรับใบเสนอราคาคือ status_change ที่เข้าสู่ขั้น Order
ซึ่งกติกาของแผน 09 พับเก็บไว้หลังปุ่ม "การเปลี่ยนสถานะ" ขั้นนี้จึงเหลือแถวเดียว

เฉพาะขั้น quote จึงให้ status_change แสดงเป็นแถวปกติ ขั้นอื่นยังพับตามเดิม
เพราะมี milestone ของตัวเองพอที่จะเล่าเรื่องอยู่แล้ว

## สิ่งที่แก้

`src/app/(app)/leads/[id]/page.tsx` เท่านั้น

- เพิ่ม `SLA_AFTER_MILESTONE_SECTIONS` ระดับโมดูล
- `timelineItems` เรียงด้วยคีย์ใหม่ `slaLast` ก่อน `sortAt`

ไม่มีแถวไหนถูกซ่อนหรือยุบ — ยังเห็นครบทั้ง milestone และ SLA
กลุ่มพับ "ประวัติการแก้ไขนัด" ยังเกาะกับแถวนัดที่ยังมีผลตามเดิม
เพราะผูกกับตัว row ไม่ใช่ตำแหน่งในลิสต์ และตัวเลข x/y ที่หัวขั้นไม่เปลี่ยน
เพราะนับจำนวน ไม่ได้นับลำดับ

## บทสรุปหลังใช้งานจริง

ไล่ดูทีละขั้นแล้วได้ข้อสรุปเดียวกันทุกขั้น: **แถว SLA ควรอยู่ตรงเวลาที่นาฬิกา
เริ่มเดิน** เพราะจุดเริ่มมาก่อนงานที่มันวัดเสมอ

| ขั้น | นาฬิกาเริ่มเมื่อ | งานที่วัด |
| --- | --- | --- |
| Survey | วันนัดที่ยืนยันแล้ว | เข้าสำรวจหน้างาน |
| Quotation | สำรวจเสร็จ | ลูกค้าตอบรับใบเสนอราคา |
| Order | ลูกค้าตอบรับใบเสนอราคา | ชำระงวดแรก |
| Install | ยืนยันเงินมัดจำ | นัดติดตั้ง, ติดตั้งเสร็จ |

อ่านจากบนลงล่างจึงได้เรื่องว่า "นาฬิกาเริ่มตรงนี้ แล้วเหตุการณ์ต่อจากนี้
คือคำตอบของมัน" ซึ่งเป็นสิ่งที่การดันแถว SLA ไปท้ายขั้นทำลายทิ้ง

เมื่อ timestamp ชนกัน milestone ยังขึ้นก่อน SLA ตาม `tiePriority` เหมือนเดิม
