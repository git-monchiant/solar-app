### ที่เปลี่ยนจากแบบร่าง

- ค่าคงที่อยู่ใน `load-assumption.ts` ไม่ใช่ `customer-questionnaire.ts` — ไฟล์นี้ต้องไม่มี import เพื่อให้เทสต์รันด้วย `--experimental-strip-types` ได้
- คีย์แอร์ใน JSON เป็น `"ac": { "day_h", "night_h" }` (ไม่ใช่ `ac_hours`) ให้รูปเดียวกับอุปกรณ์อื่น · มีคีย์ `"unknown": true` สำหรับ "ไม่ทราบ"
- ตู้เย็นคิดเป็น 50 W เฉลี่ย × 24 ชม. (≈1.2 kWh/วัน) เพื่อให้ทุกแถวใช้สูตร จำนวน × กำลังไฟ × ชั่วโมง เหมือนกัน
- `LEGACY_PEAK_USAGE` ย้ายมา export จาก `customer-questionnaire.ts` (label ล้วน) Dashboard III เติม "(ข้อมูลเดิม)" เอง
- "% ของค่าไฟจริง" พิมพ์เฉพาะเมื่อถามครบทุกข้อแล้ว — ถ้ากรอกครึ่งเดียวตัวเลขจะต่ำจนดูเหมือนข้อค้นพบ
- ตาราง §3 ใช้ `table-layout:fixed` เพราะรายการแอร์ยาว ๆ บีบหัวคอลัมน์ชั่วโมง

### 2. ที่เก็บข้อมูล — คอลัมน์ใหม่ 1 คอลัมน์

`lead_data.load_profile NVARCHAR(MAX) NULL` เก็บ JSON แบบเดียวกับ `ac_split`
(8 อุปกรณ์ × 2–4 ค่า ถ้าแตกเป็นคอลัมน์จะได้ราว 20 คอลัมน์ และไม่มีใครต้อง filter ด้วย SQL)

```json
{
  "v": 1,
  "ac_hours":     { "day": 6, "night": 8 },
  "fridge":       { "qty": 1 },
  "water_heater": { "qty": 2, "day_min": 0, "night_min": 30 },
  "water_pump":   { "qty": 1, "day_h": 1, "night_h": 0 },
  "washer":       { "loads_per_week": 4, "period": "day" },
  "electronics":  { "qty": 3, "day_h": 4, "night_h": 5 },
  "lighting":     { "qty": 15, "day_h": 0, "night_h": 5 },
  "ev":           { "charger_kw": 7.4, "sessions_per_week": 3, "hours_per_session": 4 }
}
```

กติกา:

- **ไม่มีคีย์ = ยังไม่ได้ถาม** → รายงานเว้นช่องว่างให้เขียนมือ
- **`qty: 0` = ไม่มีอุปกรณ์นี้** → รายงานพิมพ์ 0 / 0 kWh (เป็นคำตอบจริง ไม่ใช่ข้อมูลหาย
  แนวเดียวกับ `no_answer` ของ `HOUSEHOLD_INCOMES` ใน [customer-questionnaire.ts:217-231](../../src/lib/customer-questionnaire.ts))
- **ห้ามใส่ชั่วโมงแอร์ลงใน `ac_split`** — Dashboard III รวมทุกค่าใต้ `day` / `night` เป็นจำนวนเครื่อง
  ([customer-dashboard-data.ts:171-177](../../src/lib/customer-dashboard-data.ts)) ใส่คีย์ชั่วโมงเข้าไปจะทำให้จำนวนแอร์เพี้ยน
- ช่วงชาร์จ EV ยังอยู่ที่ `ev_charge_period` เดิม ไม่ย้าย

### 3. ตัวคำนวณกลาง

ไฟล์ใหม่ `src/lib/load-assumption.ts` เป็น pure function

```ts
computeLoad(leadData) → {
  rows: [{ key, label, qty, kw, dayHours, nightHours, dayKwh, nightKwh }],  // null = ยังไม่ได้ถาม
  dayKwh, nightKwh, nightShare,   // null ถ้าไม่มีแถวไหนคำนวณได้เลย
  answeredRows, totalRows
}
```

ใช้ร่วมกันระหว่างผลรวมสดในฟอร์ม (ข้อ 1) และรายงาน (ข้อ 4) ตัวเลขสองที่จึงไม่มีทางไม่ตรงกัน

### 4. รายงาน §3

- เติมทุกคอลัมน์จาก `computeLoad()` แถวไหนยังไม่ได้ถามคงช่องว่างไว้เหมือนเดิม
- **ลบค่าตายตัว** ของตู้เย็น/ปั๊ม/ซักผ้า — ไม่ได้ถามก็ว่าง
- **เพิ่มแถว EV** แทนแถว "เครื่องใช้ไฟฟ้าเด่น"
- แถวรวมพิมพ์ kWh/วัน กลางวันและกลางคืน + บรรทัด "สัดส่วนใช้ไฟกลางคืน ≈ Z%" (D3 ตัดสินว่าจะเน้นคำแนะนำ Battery ไหม)
- **เทียบกับค่าไฟจริง**: `(dayKwh + nightKwh) × 30 × ค่าไฟต่อหน่วย` เทียบกับ `monthly_bill`
  แล้วพิมพ์ "ข้อสมมติฐานนี้ครอบคลุม ≈ N% ของค่าไฟจริง" ให้เห็นว่าคำตอบครบแค่ไหน
  ค่าไฟต่อหน่วยใช้ `financial.inputs.electricity_rate` ของใบเสนอราคาเมื่อมี
  ถ้าไม่มี (ทาง `/api/survey-report`) ใช้ 5 ฿/kWh เท่ากับที่ `calcLoan` ใช้อยู่ ([survey-report.js:48](../../src/lib/docs/survey-report.js))
- **ความเสี่ยงล้นหน้า**: §3 ถูกบีบให้อยู่หน้าเดียว ([survey-report.js:245](../../src/lib/docs/survey-report.js))
  และเลขหน้าในสารบัญเขียนตายตัว ([survey-report.js:196](../../src/lib/docs/survey-report.js))
  ถ้าเพิ่มแถว EV + บรรทัดสรุปแล้วล้นไปหน้า 7 สารบัญจะผิดทั้งเล่ม ต้องตรวจ PDF จริงกับลีดที่ตอบครบทุกแถว
