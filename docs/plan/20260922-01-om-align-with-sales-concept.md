#### 4.1 ★ ผู้ใช้เปลี่ยนแนวทาง 24 ก.ย. 69 — งาน O&M อยู่ในการ์ด O&M ก่อน

**เดิม** ผมทำแท็บ "งาน O&M ของฉัน" ไว้บนหน้า Today แล้วพบว่า **เมนูซ้ายของโมดูล O&M ไม่มี Today**
(Sales กับ สำรวจ&ติดตั้ง มี) ⇒ คนที่ทำงานในโมดูล O&M ไปไม่ถึงแท็บนั้นเลย

**ผู้ใช้เคาะ:** ให้งาน O&M อยู่ในโมดูลตัวเองให้สมบูรณ์ก่อน **ซ่อนจาก Today ให้สนิท** แล้วค่อยย้ายขึ้นหน้ารวมทีหลัง
เหตุผล: Today เป็นหน้าที่ทีมขายเปิดทุกวัน เอาของที่ยังไม่นิ่งไปแปะเสี่ยงกวนคนที่ไม่ได้ทำ O&M
(ตรงกับแบบแผนของโปรเจกต์: โมดูล `Package O&M` ก็ติดป้าย "เร็วๆ นี้" รอจนพร้อม)

**ที่ทำตามนั้น**
- **ถอดแท็บออกจาก `today/page.tsx` ทั้งหมด** — tab key · state · fetch · section · import (เหลือ 0 ร่องรอย)
  ของเดิมอยู่ใน commit `2be9c74` เอากลับมาได้เมื่อพร้อม
- แทนด้วย **ติ๊ก "งานของฉัน" ในหน้างานบริการ** ยกบล็อกจาก Pipeline ทั้งก้อน รวมการจำค่าไว้
  (`om.services.mineOnly` ใน localStorage) ⇒ ตอบ "งานของฉัน" ได้โดยไม่ต้องออกจากโมดูล
- ตัวกรองเป็นแบบ **ซ้อนบนแท็บ** ไม่ใช่ตัวแทน และ**ตัวเลขบนแท็บขยับตามด้วย**
  ตามกติกา Pipeline: *"ตัวเลขบนชิปต้องเป็นจำนวนที่จะเห็นจริงเมื่อกด"*

**เกณฑ์ว่าเมื่อไหร่ค่อยย้ายขึ้น Today:** เฟส 5 (SLA) + เฟส 6 (แจ้งเตือน) เสร็จ
— ถึงตอนนั้นตัวเลขบน Today ถึงจะมีความหมาย ไม่ใช่แค่ลิสต์เฉย ๆ

**หมายเหตุสำคัญ:** เจ้าของเคส **ไม่ใช่ประตูล็อก** — ว่างไว้ได้ ใครเปิดหน้าก็ยังทำงานต่อได้
ตามที่ผู้ใช้เคาะ 10 ก.ย. ("ไม่มีเจ้าของงาน ใครเปิดหน้านี้ก็โทรต่อได้") มีไว้เพื่อให้ Today ถามได้ว่า "งานของฉัน" เท่านั้น

## 1. ปัญหาตอนนี้: O&M เป็นเกาะ

O&M ทำงานได้ครบและคุณภาพโค้ดดี แต่ถูกสร้างขนานกับระบบ ไม่ได้สร้างบนระบบ — วัดจากโค้ดจริง:

| จุดเชื่อม | ฝั่งขายมี | O&M |
|---|---|---|
| journey code (`journey_step/sub`) | ✅ ทุกเมนูผูก code | ❌ ไม่มีเลย |
| badge บนการ์ด hub / เมนูซ้าย | ✅ จาก `/api/journey-summary` | ❌ `countForModule()` คืน `null` → การ์ดไม่มีเลข |
| หน้า list กลาง | ✅ `/pipeline?tab=` ใบเดียว 16 แท็บ | ❌ 8 เมนู = 8 หน้าเขียนเอง |
| หน้า detail ของงาน | ✅ `/leads/[id]` (3,188 บรรทัด) | ❌ ไม่มี — ทำงานใน drawer |
| `ListPageHeader` / `LeadCard` | ✅ ใช้ร่วมทุกหน้า | ❌ เขียน header/การ์ดเองทุกหน้า |
| SLA | ✅ 12 policy + sweep + ชิปกรอง | ❌ ไม่มี |
| Activity timeline | ✅ `ActivityTimeline` + `lead-activity-log` | ⚠️ มี log แต่ไม่มี UI timeline |
| หน้า Today | ✅ ศูนย์รวมงานประจำวัน | ❌ ไม่ปรากฏเลย (`grep om_` = 0) |
| แจ้งเตือน (`/api/notifications`) | ✅ | ❌ ไม่มี |
| Dashboard | ✅ 4 หน้า | ❌ ไม่มีตัวเลข O&M |
| ปฏิทินกลาง `/calendar` | ✅ | ❌ O&M มีปฏิทินของตัวเองแยก |
| แถบล่าง mobile | ✅ `mobileBarForRoles` 4 ชุด | ❌ ไม่มีชุดของ O&M |

**ผลที่ผู้ใช้เจอ:** เข้า hub แล้วการ์ด O&M ไม่มีตัวเลขบอกว่ามีงานค้างกี่ชิ้น (ทุกโมดูลอื่นมี) · เปิด Today ไม่เห็นงาน O&M ของตัวเอง · ต้องจำว่าคำว่า "ติดตาม" ใน Sales กับใน O&M เป็นคนละเรื่อง

## 2. Concept ฝั่งขาย 8 เสา (สรุปจากโค้ดจริง ไม่ใช่จากความจำ)

1. **ทะเบียนเลข journey ที่เดียว** — [journey-rules.mjs](../../src/lib/journey-rules.mjs) + ตาราง `journey_steps` · step เว้นทีละ 100 · sub ฝังเลข step เว้นทีละ 10 · แทรกขั้นใหม่ใช้เลขกลางช่อง
2. **เก็บขั้นลง record ตรงๆ ไม่ derive** — `leads.journey_step/journey_sub` · `refreshJourney()` เรียกหลังทุก mutation · เพี้ยนเมื่อไหร่มี nightly backfill เกลี่ย
3. **หน้า list ใบเดียว หลายแท็บ** — ทุกเมนูของทุกโมดูลชี้ `/pipeline?tab=xxx` ไม่ใช่เมนูละหน้า
4. **เมนู = กลุ่ม journey code** — `steps: [400]` / `subs: [710]` ใน [modules.tsx](../../src/lib/modules.tsx) เป็นตัวขับ badge ทั้งหมด
5. **badge = จำนวนที่กดเข้าไปเห็นจริง** — `countForModule()` นับจาก union ของ set ไม่ซ้ำ (บวกเลขรายเมนูตรงๆ ไม่ได้ เพราะเมนู "ทั้งหมด" ทับกับเมนูรายขั้น)
6. **การ์ด → หน้า detail เดียว** — `LeadCard` → `/leads/[id]` ที่มี `StatusPipeline` + `ActivityTimeline` + `LeadSlaTracking` + `QuickActionBar` ครบในหน้าเดียว
7. **SLA เป็นเครื่องยนต์กลาง** — policy เป็นตาราง, `sla-sweep` เดินนาฬิกาเอง, ชิปกรองใช้ร่วม Today/Pipeline ผ่าน [sla-filter.ts](../../src/lib/sla-filter.ts)
8. **navigation ขับด้วย role ที่ registry เดียว** — โมดูลกรองด้วย `roles` · แถบล่าง mobile ตาม role ไม่ตามโมดูล · เมนูคิวประจำตัว inject ต่อท้ายทุกโมดูล

## 3. สี่เรื่องที่ต้องเคาะก่อนเริ่ม

### 3.1 เลข journey ของ O&M — เสนอ **สาย 2000 แยกจาก lead**

เหตุผล: ฝั่งขาย 1 แถว = 1 ลูกค้า (`leads`) · O&M 1 แถว = 1 ใบงาน (`om_bookings`) บ้านหลังเดียวมีได้หลายใบข้ามปี ถ้ายัดลง `leads.journey_step` จะทับขั้นของงานขายทันที

แมป 1:1 กับ `BOOKING_STATUS` ที่ผู้ใช้เคาะไปแล้ว 7 ก.ย. — **ไม่เปลี่ยนพฤติกรรมอะไรเลย แค่ให้เลขประจำตัว**:

| code | ป้าย | = สถานะเดิมใน [booking.ts](../../src/lib/om/booking.ts) |
|---|---|---|
| 2100 | ติดตาม | `follow` |
| 2200 | ทำนัด | `pending` |
| 2300 | รอ O&M | `confirmed` |
| 2400 | เข้า O&M | `progress` |
| 2500 | รอลูกค้ายืนยัน | `checked` |
| 2600 | ปิดงาน | `closed` |
| 2800 | ยกเลิก | `cancelled` |
| 2900 | ลูกค้าไม่อยู่บ้าน | `no_show` |

**ของแถมที่ได้ฟรี:** `/api/journey-summary` คืน `{journey_step, journey_sub, n}` แบบ flat และ `getOmDb()` = `getDb()` ตัวเดียวกัน (มี guard แค่ว่า DB ต้องลงท้าย v3) ⇒ **แค่ UNION query เพิ่มเข้าไป** แล้ว `countForMenuItem()` / `countForModule()` ใช้ได้ทันทีโดยไม่ต้องแก้แม้แต่บรรทัดเดียว

#### ⚠️ 2100 นับจาก `om_bookings` ไม่ได้ — วัดกับข้อมูลจริง 22 ก.ย. 69

| | จำนวนจริงบน `solardb_v3` |
|---|---|
| `om_bookings` (ใบงานทั้งหมด) | **2** |
| บ้านถึงรอบล้าง (เกณฑ์แท็บติดตาม) | **1,847** |

แท็บ "ติดตาม" **คำนวณสด ไม่มีแถวงานรอไว้** ([follow/route.ts:85-96](../../src/app/api/om/follow/route.ts)) — แถวใบงานเกิดตอนโทรแล้วได้ความเท่านั้น (ผู้ใช้เคาะ 10 ก.ย.)
ถ้า UNION จาก `om_bookings` อย่างเดียว **การ์ด O&M จะขึ้นเลข 2 ทั้งที่มีงานโทรค้าง 1,847 หลัง** — ผิดหนักกว่าไม่มี badge เสียอีก

**แก้:** journey-summary ของ O&M ต้องเป็น **สองท่อน**
- ท่อน A → `2100` นับจาก `om_houses` (คำนวณสดเหมือนหน้า follow)
- ท่อน B → `2200`–`2900` นับจาก `om_bookings` GROUP BY `status`

**และกันนับซ้ำ:** บ้านที่ถึงรอบ *และ* มีใบงานค้างอยู่แล้ว จะโผล่ทั้งสองท่อน ⇒ ท่อน A ต้องตัดบ้านที่มีใบงานค้างออก (นับเฉพาะ "งานโทรที่ยังไม่มีใครแตะ")
ผลคือ badge ของแท็บติดตามจะน้อยกว่าจำนวนแถวที่กดเข้าไปเห็นเล็กน้อย (หน้าจอรวมบ้านที่มีใบงานค้าง + ปิดงานใน 90 วันด้วย) — **จุดนี้ต้องให้ผู้ใช้เคาะ** ว่าเอาแบบไหน:
- (ก) badge = งานค้างจริงไม่ทับกัน ← เสนอ (การ์ดโมดูลตอบคำถาม "ค้างกี่ชิ้น" ได้ถูก)
- (ข) badge = จำนวนแถวที่เห็นเป๊ะ แล้วให้เมนูติดตามติด `noModuleCount` ไม่บวกเข้าการ์ด

### 3.2 หน้า list — เสนอ **ไม่ยุบเข้า `/pipeline`**

`/pipeline` query ตาราง `leads` ทั้งหน้า คนละ entity กับ `om_bookings` · ยุบเข้าไปจะได้โค้ดเต็มไปด้วย `if (isOm)`
**แทนที่ด้วย:** `/om/services?tab=` คงไว้ แต่เปลี่ยน**โครงหน้า**ให้เหมือนกันเป๊ะ — ใช้ `ListPageHeader` ตัวเดียวกัน, slot `tabsLeft`/`tabsRight` เหมือนกัน, การ์ดทรงเดียวกับ `LeadCard`
*เหมือน concept = เหมือนรูปร่างและวิธีใช้ ไม่ใช่เหมือนไฟล์*

### 3.3 โครงสร้างทีม — เสนอ **เก็บ `om_teams` ไว้ + เพิ่มเจ้าของงาน**

สองระบบนี้ไม่ใช่ของซ้ำกัน ทำคนละหน้าที่:

| | ฝั่งขาย | O&M |
|---|---|---|
| หน่วย | `leads.owner` = คน 1 คน | `om_teams` = ทีมช่าง มี capacity/สี/วันหยุด |
| ใช้ทำอะไร | ใครรับผิดชอบลูกค้ารายนี้ | จ่ายคิวลงปฏิทิน เช็กความจุต่อช่วง |

`om_teams` มีของที่ฝั่งขายไม่มี (`capacity_override`, `color`, `om_slot_config`, `om_calendar_blocks`) — **ทิ้งไม่ได้**

#### ฝั่งขายไม่ได้มีเจ้าของคนเดียว — มี 3 ชั้น (วัดจริง 23 ก.ย. 69)

| คอลัมน์บน `leads` | คือ | มีค่า |
|---|---|---|
| `assigned_user_id` | เจ้าของเคส | 473 / 523 |
| `survey_assigned_user_id` | คนไปสำรวจ | 81 |
| `install_assigned_user_id` | คนไปติดตั้ง | 22 |

แถม `lead_sla_instances.owner_user_id` ผูกเจ้าของไว้รายงาน SLA อีกชั้น (2,027 / 2,050)

⇒ แพทเทิร์นจริงของฝั่งขายคือ **"เจ้าของเคส 1 คน + คนลงมือแต่ละช่วง"** ซึ่งตรงกับ O&M พอดี (เจ้าของเคส + ทีมช่าง)
O&M มี `om_bookings.team_id` (คนลงมือ) แล้ว **ขาดแค่เจ้าของเคส**

**เสนอ:** เพิ่ม `om_bookings.owner_user_id` · ทีมช่างยังเป็นฟิลด์แยกเหมือนเดิมตามที่เคาะไว้ 7 ก.ย.

**ของค้างที่เจอ:** `om_teams` มี 3 ทีม แต่ `om_team_members` = **0 แถว** — ทีมมีแต่ชื่อ ยังไม่ได้ใส่คนเข้าไปเลย ต้องเติมก่อนเฟส 4 ถึงจะใช้งานได้จริง

**role:** ไม่เพิ่ม role ใหม่ ใช้ 7 ตัวเดิมจาก [role-permissions.ts](../../src/lib/role-permissions.ts) — O&M อยู่ในมือ solar/solar_sup เป็นหลักอยู่แล้ว

### 3.4 SLA — เสนอ **ทำ แต่เฟสท้าย และตั้งแค่ 3 policy**

ฝั่งขายมี **15 policy · 2,050 ใบ · เลยกำหนด 305** (วัดจริง 23 ก.ย. 69) — อย่ายกมาทั้งชุด

| policy ฝั่งขาย | ใบ | เลยกำหนด |
|---|---|---|
| GRADE_PLAYBOOK | 474 | 0 |
| BOOK_SURVEY | 308 | **230** |
| ASSIGN_OWNER | 308 | 0 |
| ELECTRICITY_ASSESSMENT | 304 | 19 |
| FIRST_CONTACT | 295 | 0 |
| (อีก 10 ตัว) | 361 | 56 |

ที่ใช้ได้จริงกับ O&M มี 3: `FOLLOW_CALL` (ถึงรอบล้างแล้วยังไม่โทรภายใน X วัน) · `BOOKING_CONFIRM` (นัดแล้วยังไม่ยืนยัน) · `JOB_CLOSE` (ทำเสร็จแล้วยังไม่ปิดใบ)
ค่าทั้งหมดต้องอยู่ `om_settings` ไม่ hardcode (กติกาที่ผู้ใช้เคาะ 31 ส.ค.)
**ต้องมีข้อ 3 ก่อน** — SLA ฝั่งขายผูก `owner_user_id` ทุกใบ ถ้า O&M ไม่มีเจ้าของเคส ก็ไม่มีใครให้ทวง

5. **"ไม่มั่นใจ = เข้าคิวให้คนตัดสิน"** — `om_match_queue` ไม่มี counterpart ฝั่งขาย
6. **แยกคีย์ LINE คนละ channel** — ห้ามรวม

## 7. บั๊ก `Flow` — ✅ แก้แล้ว 23 ก.ย. 69 (ในเฟส 2)
